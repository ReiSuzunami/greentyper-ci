# Technology Benchmarks

## Status

The versioned benchmark runner is implemented. It distinguishes release candidate, comparison, implementation, workload, fixture, process mode, and operation boundary; retains every raw sample and correctness digest; and reuses the acceptance CPU guard, host fingerprint, redaction, hashes, and no-clobber evidence commit.

The default runner compiles only `harness/sha256-loop`, which validates the pipeline. The optional `bench-storage` feature compiles SQLite WAL and checksummed append-log candidates against eight explicit workloads: `critical-append-replay`, `bounded-streaming-replay`, `timer-expiry-streaming-replay`, `cas-one-winner`, `backup-restore`, `interrupted-migration`, `cross-process-crash-replay`, and the SQLite-only `sqlite-vfs-fault-recovery`. The optional `bench-terminal` feature compiles direct VT cell-grid diff and Ratatui/Crossterm candidates against one `render-matrix` workload. The optional `bench-transport` feature compiles Reqwest/Rustls on every supported host and Wrest's native WinHTTP path on Windows against one `loopback-sse` workload. The candidate-specific `bench-allocator-system`, `bench-allocator-mimalloc`, and `bench-allocator-snmalloc` features compile one process-global allocator per isolated runner against `allocation-pressure`. The runner requires `--workload`; evidence therefore cannot silently change boundaries while retaining only a comparison and implementation name.

The implemented matrix proves identical canonical replay, WAL `synchronous=FULL`, synchronous append-log commits, max-event bounded streaming batches, deterministic virtual-clock flushes at the 250ms deadline, one-winner cross-process stale-head CAS, verified backup/restore, cross-process transactional or generation-based old-or-new migration recovery, exhaustive two-transaction tail-cut classification, checksum rejection, bounded framing, and per-run timing and size evidence. The CAS workload waits until eight authenticated child contenders are ready, releases one start barrier, serializes each candidate at the store boundary, and requires one durable winner plus seven explicit stale-head losers before parent replay. The migration workload starts three authenticated children from independent v1 stores and kills them after an early unpublished candidate, a complete unpublished candidate, or a published v2 generation; restart must expose exactly two complete v1 states and one complete v2 state with identical canonical events. The timer workload never sleeps: fixed arrivals produce batch sizes `[3, 4, 1, 3]` and record deadline, event-limit, and final-drain flushes for both candidates. The crash workload launches and forcibly terminates the feature-built candidate child before write, at four transaction progress points, and after sync before acknowledgement. Restart must safely write once, remain ambiguous-blocked, or recognize the durable transaction without repeating it; both candidates emit the same correctness digest. The SQLite-only VFS workload registers a non-default connection-scoped wrapper around the platform VFS, injects a rejected first WAL write, a partial first WAL write followed by `SQLITE_IOERR_WRITE`, and a rejected first WAL sync, then disables injection, reopens normally, runs `PRAGMA integrity_check`, and accepts only complete transaction prefixes. It classifies the two write failures as known-not-repeated and the sync failure as ambiguous-blocked. Existing process-crash progress points still exercise transaction rollback; the VFS workload adds synthetic WAL I/O and short-write evidence, not real power-loss or torn-hardware proof.

The terminal matrix renders 27 canonical frames across 40x12, 80x24, and 160x50 viewports. Each size covers a baseline, model-equality no-op suppression, a status update, four streaming updates, the hierarchical Slash Panel, and a clearing frame that removes prior content. Both candidates resize a live renderer, replay their ANSI bytes through the same VT parser, and must reproduce every symbol, style, wide-character continuation, cleared cell, and final digest; every no-op produces zero bytes. The workload records render, resize, replay, byte, cell, and write-count evidence. The first product tracer uses the Direct VT strategy and now includes one narrow statusline-preset Config editor, but neither slice is the final technology selection. The evidence does not yet prove real ConPTY input, process startup, stable-idle CPU or memory, or the Performance Contract's P0/P1 budgets.

The transport matrix starts private loopback origin and explicit-proxy servers for every sample. Seven requests cover cold and warm SSE, fragmented UTF-8 plus CRLF/LF framing, HTTP 503, a body deadline, cancellation after the first event, an explicit proxy route to a synthetic hostname, and a custom origin carrying a synthetic credential binding. Both candidates must produce the same canonical event digest; the proxy must observe no authorization bytes. Server setup, fixture parsing, and evidence I/O remain outside the named client boundary. This first workload is HTTP-only and does not yet prove HTTPS/TLS policy, proxy authentication or system-proxy behavior, live-provider behavior, resource budgets, or a transport selection.

The allocator workload executes the same bounded allocation, deterministic growth, mutation, sampling, and release schedule in three separately built binaries. Candidate identity records the system allocator or the locked Mimalloc/Snmalloc dependency and feature policy; CI requires identical output digests and distinct executable/dependency fingerprints. Reported payload gauges are workload facts, not operating-system memory evidence.

These are not storage, terminal, transport, or allocator decisions. Storage still requires additional approval/tool-effect durability boundaries, fuzzing, real power-loss evidence, same-commit 30-run FMDev evidence for every workload, and Windows directory-entry durability evidence. Terminal still requires Windows correctness beyond the in-memory VT oracle, same-commit FMDev runs, resource measurements, and a recorded selection. Transport still requires its HTTPS/TLS, proxy-authentication, Windows runtime, fuzz, resource, and same-commit FMDev gates. Allocator still requires cold-start, stable-idle, streaming, Agent-load, context-pressure return-to-idle, Windows process-tree resource evidence, comparable CRT proof, same-commit FMDev runs, and a recorded selection.

## Decision Rule

Every comparison uses the same source revision, locked dependencies, x86-64-v3 build policy, fixture version, FMDev shape, warmup policy, and at least 30 measured runs per implementation. Correctness, recovery, security, and packaging are pass/fail gates before timing is considered. Raw p50, p95, minimum, maximum, standard deviation, resource measurements, artifact size, and dependency cost remain visible.

An absolute Performance Contract violation blocks a candidate. A repeatable regression above 5% warns and above 10% blocks. When measured results are within noise, prefer the smaller dependency and maintenance surface. A microbenchmark or CI smoke cannot approve a choice.

Storage, terminal, transport, Mimalloc 0.1.52, and Snmalloc 0.7.4 candidate versions are fixed in `Cargo.lock`. Snmalloc uses its default CMake and WaitOnAddress features with `native-cpu` disabled. Its Windows MSVC build adds `/wd4864` because Snmalloc 0.7.4 treats the diagnostic introduced by MSVC 19.51 as an error through upstream `/WX`; every other compiler warning remains an error, and the flag is bound into candidate evidence. Mimalloc uses no default features and does not enable process-wide override symbols. Jemalloc is excluded from the primary Windows MSVC comparison because its maintained Rust wrappers do not present it as a supported MSVC target.

## Workload Isolation

In-process operations report only their declared operation boundary; fixture parsing, executable hashing, host fingerprinting, serialization, and evidence I/O remain outside the timed region. Allocator and other process-global candidates run as separate binaries. Process launch is reported independently unless the named workload is explicitly cold start.

Candidate adapters remain inside the acceptance package or package-local benchmark targets until selected. Provider wire types, terminal backends, storage engines, and global allocators do not leak into canonical core interfaces during comparison.
